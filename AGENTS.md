- Reto 2.700 lives in separate `reto_*` tables keyed by event_id; reciprocal connections are computed in the DB, never stored or trusted from the browser — keeps the existing likes/matches/meetings untouched.
- Closing the Reto freezes results into `reto_snapshots`/`reto_snapshot_pairs` and `reto_scoreboard`/`reto_connection_count` read the snapshot while closed — prizes come from a stable, auditable copy; all admin writes go through `reto_admin_*` SECURITY DEFINER functions that check super_admin.
- Reto 2.700 end-to-end checks live in `scripts/reto-2700/simulacion.ts` (run with bun); it only touches the hidden TEST event, verifies real data is unchanged and leaves the test event clean — rerun it after any `reto_*` SQL change.

- Open chat is person-to-person in `chat_dm` (user_a < user_b); sending is gated in RLS by `chat_dm_allowed` (both active empresa/solución profiles) — permission lives in the DB, not the UI. Old `chat_messages` is kept unused.
- Meeting proposals come from the pure engine in `src/lib/meeting-generator.ts` (tested), fed by event rules + availability; nothing is written until the admin approves the draft — keeps scheduling rules testable and reversible.
- Event membership = an account with at least one non-cancelled `event_registrations` row; every panel (admin and participant) scopes accounts, likes, matches, meetings and notices through `src/lib/event-scope.server.ts` (`getEventScope`, `pickCurrentEvent`) — keeps each event fully independent with one shared definition.
- List filtering and alphabetical ordering live in pure, vitest-covered helpers under `src/lib` (e.g. `registration-list.ts`) that routes call; routes keep only state and markup — keeps who-is-shown-and-in-what-order checkable without a browser session.
- 1to1 meetings are hidden from participants until `events.meetings_published` is true; enforced in the `meetings_1to1` read policy and the notify trigger via `meetings_visible()` — admins can edit drafts safely without leaking or notifying.
- The acting responsable of an empresa/solución account is resolved by `resolveAccountOwner` in `src/lib/account-owner.ts` (valid `user_id`, else active owner/member); participant lists use `getMyEventScope().accountOwners` — "Me interesa" never disappears because an account's `user_id` is empty.
- Meeting filters, creation and availability share `buildMeetingParticipants`, keyed by event account IDs with active members and resolved owners; paginate source reads — legacy owner links must not hide registered accounts.
- Participant dashboard activity uses authenticated account-scoped reads and paginated results; matches count unique partner accounts, meetings count scheduled non-cancelled rows — teammates see consistent totals without truncation.
- Account administrator transfers use a service-only transactional RPC after authenticated superadministrator validation; lock the account and its members, demote the previous owner and promote the target together — concurrent transfers cannot leave multiple owners.
- Solution highlights are keyed by event and solution account in event_featured_solutions, with superadmin-only writes enforced by RLS; only the empresa solution directory consumes them — avoids global priority or changes to selections.
- Directory order is stored per event and target kind with superadmin-only writes; the pure directory-order helper counts unique incoming source accounts, prioritizes highlights in every mode and keeps shuffled ranks stable per visit — independent lists without changing interactions.
- Participant selection summaries and incoming/outgoing detail reuse the event-scoped admin selections read and the pure participant-selections helper, keyed by account IDs — keeps counts consistent without new writes or person-level duplication.
- Interactions are never deleted with people: likes/matches/meetings reference profiles with ON DELETE RESTRICT, admin deletes call `assertNoActivity`, moving a person hands their interactions to a remaining teammate (`keepInteractionsWithAccount`), and the event Participantes trash only removes event registrations — accounts keep their history whatever admin action runs.
- Selection reminders use authenticated superadmin functions, paginated event registrations and the shared event scope, with one request per recipient and campaign-scoped email/notification idempotency — retries preserve individual delivery results without touching credentials or interactions; run their RPC unit tests with `bunx vitest run --config vitest.reminders.config.ts` to isolate mocks from application transforms.
- Individual credential exports use the credential DTO returned by the authorized password/email operation, never a second password generation — the spreadsheet and email must contain the exact password saved in Auth.
- Guide-driven 1to1 scheduling uses the pure, tested `src/lib/guided-meeting-planner.ts` (full-Talk reservations via reserveTalks, scarcity pass, closed lists for 1–6 selections, one meeting per company–sponsor pair, sponsor vetoes/priority lists, guarantees by lowest slack then tier, 5→6 reoptimization, group sessions, Talk free-DRH minimum, never unselected sponsors); each event keeps its rules in a config script under `scripts/meetings/` that writes drafts only while meetings are unpublished — rules stay replicable and auditable per event.
- Talk attendance starts in the event script's `src/data/talks-<event>.json`; superadmin removals persist per event, Talk and person/company in `event_talk_exclusions`. The panel and manual meeting availability/creation share `readEventTalks` — removals free only that person's Talk without altering other assignments.
